# ReCloud 自动化与 AI Agent 规划

> 三种角色（用户 / 管理员 / 技术人员）× 三种执行模式（人工驱动 / 定时任务 / AI Agent）

---

## 一、分类框架

| 类别 | 核心特征 | 判断标准 |
|------|---------|---------|
| **人工驱动** | 需要主观判断、承担后果、情感交互 | 做错了要有人负责 |
| **定时任务** | 规则明确、无需判断、周期性执行 | 给规则就能跑 |
| **AI Agent** | 需要理解语义、模式识别、模糊决策 | 规则写不死，需要"理解" |

## 五、AI Agent 技术方案详解

### 5.1 内容审核 Agent（优先级最高）

**技术栈：RAG + Guardrails + Human-in-the-Loop**

```
用户举报 → Agent 接收
    │
    ├─ RAG：检索相似已判案例
    │   "这条内容和之前判定的XX案例类似"
    │
    ├─ LLM 分析：结合上下文判断是否违规
    │
    ├─ Guardrails：强制结构化输出
    │   {violation_type, confidence, evidence, suggested_action}
    │
    ├─ 置信度 > 0.9 → 自动处理（删除 + 通知用户）
    ├─ 置信度 0.6~0.9 → 标记建议，推送管理员终审
    └─ 置信度 < 0.6 → 跳过，交管理员人工判断
```

**RAG 的价值**：审核标准不是固定规则，而是"案例积累"。新举报来了 → 检索历史相似判例 → LLM 参考判例决策。

**Guardrails 的价值**：LLM 输出不可控 → 强制结构化输出，防止误判导致大规模误删。

**Human-in-the-Loop 的价值**：置信度不高时必须有人兜底。管理员终审结果作为新案例进入 RAG 知识库，形成闭环。

### 5.2 批注质量分析 Agent

**技术栈：Multi-Agent 协作（CrewAI 模式）**

```
一条新批注产生 → 触发分析流水线
    │
    ├─ Agent A（内容分析员）：
    │   ├─ RAG 检索原文上下文
    │   ├─ 评估：深度、准确性、启发性
    │   └─ 输出：{depth_score, accuracy_score, insight_score}
    │
    ├─ Agent B（社区分析师）：
    │   ├─ 分析讨论热度、互动数据
    │   ├─ 对比同章节其他批注
    │   └─ 输出：{engagement_score, uniqueness_score}
    │
    └─ Agent C（评审官）：
        ├─ 综合 A、B 分析结果
        ├─ 最终决策：精选/普通/低质
        └─ 生成评语
```

**Multi-Agent 的价值**：单一 Agent 容易"偏科"。多角色协作 = 多维度评估，每个 Agent 职责单一，prompt 更精准。

### 5.3 用户行为分析 Agent

**技术栈：Agent Memory + Function Calling**

```
Agent Memory 结构：
├─ 短期记忆：最近 24h 操作序列
│  "用户A: 创建批注5条, 被举报2次, 删除1条"
├─ 长期记忆：历史行为画像
│  "用户A: 注册30天, 累计批注50条, 举报率4%"
└─ 工作记忆：当前分析上下文

Function Calling 工具：
├─ get_user_stats(userId)
├─ get_recent_reports(userId)
├─ get_annotation_similarity(userId)
└─ suggest_action(userId)
```

**Agent Memory 的价值**：行为分析需要"记住"历史模式。短期记忆捕捉突发异常，长期记忆识别慢性问题。

### 5.4 运营决策 Agent

**技术栈：Agentic Workflow（Plan → Execute → Reflect）**

```
管理员问："这周社区状况怎么样？"
    │
    ├─ 规划（Planning）：
    │   "需要查：用户增长、批注活跃度、举报处理率、异常事件"
    │
    ├─ 执行（Execution via Function Calling）：
    │   ├─ get_weekly_user_growth()
    │   ├─ get_annotation_trend()
    │   ├─ get_report_resolution_rate()
    │   └─ get_top_controversial_chapters()
    │
    ├─ 反思（Reflection）：
    │   "批注下降 + 第3章争议 → 可能是内容引发分歧。
    │    举报处理率低 → 建议 Agent 审核分担。"
    │
    └─ 输出：结构化周报 + 行动建议
```

**Agentic Workflow 的价值**：不是"查数据 → 展示"，而是"查数据 → 分析 → 建议"。Agent 自己规划、自己反思。

## 六、技术选型

| 组件 | 推荐方案 | 理由 |
|------|---------|------|
| Agent 框架 | LangGraph（Python） | 状态机模式，适合复杂流程 |
| 多 Agent 协作 | CrewAI / LangGraph | 批注质量分析需要多角色协作 |
| RAG | LangChain + ChromaDB | 历史判例检索、原文上下文检索 |
| Function Calling | OpenAI API / 本地模型 | Agent 调用 Java 后端工具 |
| Agent Memory | LangChain Memory + Redis | 短期记忆用 Redis，长期记忆用向量库 |
| Guardrails | Guardrails AI / NeMo | 约束 LLM 输出格式和安全性 |
| 评估 | LangSmith / 自建评估集 | Agent 输出质量监控 |
| Java ↔ Python 通信 | REST API / gRPC | Java 后端提供数据接口，Python Agent 调用 |

## 八、占比总结

```
              人工驱动     定时任务     AI Agent
用户侧        60%         25%         15%
管理员侧      30%         45%         25%
技术人员侧    20%         55%         25%
```

**核心规律**：
- 越靠近"判断"和"责任" → 人工
- 越靠近"重复"和"规则" → 定时任务
- 越靠近"理解"和"模式" → AI Agent
